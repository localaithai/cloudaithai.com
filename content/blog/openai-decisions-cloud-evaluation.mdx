## OpenAI เปิด API สำหรับคำตอบที่มีขอบเขต

OpenAI เปิด [Decisions API แบบ GA](https://openai.com/index/decisions-api/) วันที่ 22 ตุลาคม 2026 โดยใช้ GPT-6 Luna คืน probability, choice หรือ score จากข้อมูลที่ให้ประเมิน [ประกาศนักพัฒนา](https://community.openai.com/t/decisions-api-is-now-generally-available-with-new-updates/1408934) ยืนยันการออกจาก beta

Microsoft ระบุใน [บทความวันที่ 23 ตุลาคม](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/azure-openai-decisions-api-now-generally-available-in-microsoft-foundry/4567265) ว่านำบริการเข้า Foundry วันที่ 22 ตุลาคม เส้นทาง Azure กับ OpenAI โดยตรงต้องตรวจ endpoint และเงื่อนไขแยกกัน

## เลือกผลตอบตามการตัดสินที่ต้องใช้

ข้อเสนอสำหรับผู้ซื้อคลาวด์คือเขียนคำถามธุรกิจที่แคบพอจะรู้คำตอบถูกผิด เช่น ต้องส่งเอกสารกลับให้เจ้าของเติมหรือส่งให้ผู้ตรวจคนใด แล้วกำหนดชุดตัวเลือกที่มีทางออกเมื่อข้อมูลไม่พอ

| สิ่งที่ต้องตัดสิน | ชุดทดสอบที่ควรเตรียม | ขอบเขตการนำผลไปใช้ |
| --- | --- | --- |
| เงื่อนไขเป็นจริงหรือไม่ | ตัวอย่างจริง เท็จ และคลุมเครือ | ใช้เกณฑ์ที่ผ่านการทดสอบ |
| ควรเข้าคิวใด | งานหลายเจตนาและนอกขอบเขต | มีผู้รับผิดชอบคิวสำรอง |
| ระดับตาม rubric | ตัวอย่างขอบระหว่างระดับ | คนตรวจนิยามระดับให้ตรงกัน |
| โมเดลปฏิเสธ | คำขอที่ควรหยุดประเมิน | แยกจากคะแนนต่ำและส่งให้คน |
| เปลี่ยนเส้นทางบริการ | ข้อมูลชนิดเดียวกันแต่ต่าง endpoint | ตรวจนโยบายก่อนส่งซ้ำ |

ตารางนี้เป็นการออกแบบการประเมินที่เสนอ [คู่มือ Microsoft](https://learn.microsoft.com/azure/foundry/openai/how-to/decisions) แยก refusal ออกจากคำตอบที่มี probability ต่ำ ระบบปลายทางจึงต้องตรวจชนิดคำตอบก่อนอ่านค่า

## วัดคุณภาพก่อนเปิดให้ตัดสินงานจริง

เก็บรุ่นชุดทดสอบ prompt ตัวเลือก และ threshold ไว้ด้วยกัน เมื่อเปลี่ยนอย่างใดให้ตรวจตัวอย่างเดิมและกรณีใหม่ที่ทำผิด โดยให้เจ้าของงานตัดสินว่าความเสียหายแบบใดต้องหยุดหรือส่งต่อ

Mimir Suites Cloud ส่งข้อความเอกสารไปโมเดลคลาวด์โดยปิดบัง PII เป็นค่าเริ่มต้น วิดีโอ OpenAI ปี 2025 เป็นบริบทการสร้าง Agent ก่อน Decisions GA ใช้ [วิธีประเมินโมเดลคลาวด์](/methodology/) บันทึกทั้งผลที่ใช้ได้ การส่งต่อ และต้นทุนของงานที่ทำซ้ำ
