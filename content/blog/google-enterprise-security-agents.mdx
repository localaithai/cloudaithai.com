## ตัวอย่าง Security ชวนทบทวนสิทธิ์งานเอกสาร

Google Cloud ประกาศ security agents จากพันธมิตรวันที่ 29 กันยายน 2026 ตัวอย่าง Britive ให้คนอนุมัติก่อนถอน privileged session ข่าวไม่ใช่ผลระบบเอกสารกฎหมาย [แหล่งข่าวทางการ](https://cloud.google.com/blog/products/identity-security/google-cloud-partners-deliver-new-security-agents-and-ai-defenses-with-gemini-enterprise)

งานเอกสารกฎหมายมีทั้งค้นข้อความ ร่างข้อเสนอและการส่งหรือแก้ฉบับที่คนอื่นใช้ การให้ agent ช่วยขั้นแรกไม่ควรขยายสิทธิ์ถึงทุกขั้นโดยอัตโนมัติ ทีมควรกำหนดเจ้าของเอกสารและสิ่งที่ต้องอนุมัติก่อนเรียกเครื่องมือที่มีผลจริง ไม่ใช้คำตอบโมเดลแทนการตัดสินใจของคนรับผิดชอบ

## แบ่งการอ่านจากการกระทำที่มีผล

ข้อวิเคราะห์คือผูกการอนุมัติกับการกระทำเฉพาะ ไม่ใช่อนุมัติให้ agent ทำได้ทุกอย่างตลอด session แสดงแฟ้ม เป้าหมายและผลที่คาดก่อนให้คนยืนยัน การอนุมัติร่างข้อความไม่ได้หมายความว่าอนุญาตส่งให้ผู้รับภายนอกด้วย

| ขั้นงาน | ขอบเขตที่เสนอ |
| --- | --- |
| ค้นและอ่าน | จำกัดเอกสารที่ผู้ใช้มีสิทธิ์ |
| ร่าง | บอกว่าเป็น draft และตรวจต้นฉบับ |
| แก้หรือส่ง | แสดงฉบับ ผู้รับและขออนุมัติเฉพาะงาน |
| เปลี่ยนสิทธิ์ | คนมีอำนาจยืนยันพร้อม log การเปลี่ยน |

นี่เป็น workflow ที่เสนอ ไม่ใช่คำแนะนำข้อกฎหมายหรือ feature list ของ Gemini Enterprise ให้ผู้รับผิดชอบงานกำหนดเกณฑ์ที่เหมาะกับเอกสารจริงและตรวจว่าเครื่องมือบังคับได้

## ทดลองการอนุมัติด้วยระบบจำลอง

ใช้ระบบจำลองที่ไม่มีการส่งจริง ทดลองอนุมัติ ปฏิเสธและปล่อยคำขอหมดอายุ ตรวจว่า agent ไม่เรียกเครื่องมือก่อนอนุมัติและไม่ใช้การอนุมัติเก่ากับแฟ้มใหม่ เพิ่มกรณีเอกสารชักนำให้เปิดไฟล์อื่น เพื่อดูว่าขอบเขตสิทธิ์ยังถูกยึดตามผู้ใช้

กำหนดวิธีหยุดงานเมื่อผู้อนุมัติถอนสิทธิ์หรือแก้คำสั่ง ตรวจสิ่งที่ส่งไปแล้วแยกจากงานที่ยังรอ และให้ผู้ใช้เห็นสถานะชัด ระบบที่มีคนกดยืนยันแต่ไม่เห็นฉบับหรือผู้รับอาจยังไม่ช่วยให้ตัดสินอย่างมีข้อมูล
